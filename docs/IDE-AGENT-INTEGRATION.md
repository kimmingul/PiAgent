# IDE 통합: 개발 후보 사용 안내

**한국어** · [English](IDE-AGENT-INTEGRATION.en.md) · [문서 목록](README.md)

이 문서는 2026-10-09 작업 트리에서 검증 중인 구현을 설명한다. 소스는 현재 0.11.0
후보를 표시하며 이전 검증 receipt의 실제 0.10.0 바이너리 식별자는 유지한다. 서명 릴리즈나
모든 설치 IDE 시나리오의 검증 완료를 선언하지 않는다. [개발 계획](IDE-AGENT-ROADMAP.md)의
더 넓은 목표는 SDK 실험과 실제 사용 검증이 필요하다. 연결된 설치에서 실제로
가능한 작업은 현재 카탈로그와 기록된 검증 근거로 판단한다.

## 작업 전에 가용성 확인

IDE에서 프로젝트/솔루션을 열고 PiAgent에 연결한 뒤 채팅에 **`/ide`**를 입력하거나
설정의 IDE 기능 상태를 연다. 화면은 어댑터가 마지막으로 전달한 상태, 수집 시각,
백엔드와 작업별 가용성을 표시한다. 화면을 열 때마다 SDK를 다시 조회하지 않는다.
새 확인이 필요하면 에이전트에게 `ide_catalog` 조회를 요청한다. 어댑터의 유휴 상태
갱신과 실행 전 점검도 새 상태를 전달한다.

`supported`와 `partial` 작업은 모델에 노출할 수 있다. `partial`은 설명된 백엔드의
범위가 제한된다는 뜻이며 실패한 실행을 성공으로 인정한다는 뜻이 아니다.
`unavailable`과 `blocked` 작업은 이유를 표시하고 실행 가능한 도구에서 제외한다.
계획/읽기 전용 모드는 제어와 적용 작업을 제외한다. 실제 실행에서도 권한과 상태를
확인하며 카탈로그 가용성은 쓰기 권한을 부여하지 않는다. 이전 어댑터는 기존에
협상한 도구를 유지한다.

네이티브 OMP 18.6.1에서는 Always Ask 모드의 읽기 전용 요청에도
`Allow tool: ide_context` 카드가 나타날 수 있다. 설치된 OMP는 RPC host 도구를
실행 등급으로 분류하며 등록 스키마에서 읽기 등급을 지정할 수 없다. 이는 OMP의
외부 도구 승인 단계이며 관리자 권한 상승이나 PiAgent 변경 승인이 아니다.
카드는 읽기 범위를 설명하고 승인하면 해당 요청만 허용한다. 거절/취소하면 실행하지
않는다. PiAgent는 선택한 정책을 유지하고 자동 응답하지 않는다. 네이티브
Approve/Deny 표시만 UI 언어를 따르며 실제 응답 값과 알 수 없는 외부 선택지는
바꾸지 않는다.

개요 조사에는 `ide_context` snapshot 한 번으로 시작한다. 두 어댑터 모두 제한된
프로젝트 목록과 활성 구성/플랫폼을 이미 포함한다. 추가 정보가 필요할 때만 다른
작업을 요청한다. snapshot/projects/configurations 호출은 별도 요청이므로 각각
OMP 승인 카드가 나올 수 있다. snapshot 안내는 불필요한 호출을 줄이며 승인 정책을
우회하지 않는다. IDE 빌드·제어·적용 도구는 여전히 PiAgent의 별도 검토와 승인이 필요하다.

실제 광고된 작업만 사용할 수 있다. VS 선택 프로젝트 빌드는 프로젝트 의존성을
포함하지 않으므로 필요하면 솔루션 빌드를 사용한다. 테스트 결과는 외부 실행기 근거이며
Test Explorer 제어가 아니다. 테스트 0건, 보고서 누락, 오래된 진단이나 SDK 요청 접수만으로
성공을 판단할 수 없다.
RAD `ide_diagnostics`는 정확히 같은 워크스페이스/프로젝트/구성/플랫폼의 마지막 완료
외부 빌드 보고서만 반환하고 `mayBeStale:true`를 표시한다. 네이티브 IDE 오류 창을
열거하지 않는다. 외부 백엔드는 활성 원본 `.dpr`/`.dproj`와 `Delphi.Personality`를
확인한 뒤 `.dproj`를 해석하며 polling/진단 재사용 시 원본 경로, personality, 구성과
플랫폼을 다시 확인한다. `.cbproj`, `.dpk`, 다른 personality의 sidecar는 미지원이다.
지원되는 중첩 속성 스키마는 크기/깊이가 제한되고 컴포넌트 참조를
따라가지 않는다. Font를 포함한 중첩 scalar 필드는 구현됐으나 실제 시나리오 검증은
남아 있다. Collection authoring은 구현하지 않았다.

## 변경 미리보기와 적용

예를 들어 “이 C# 심볼 이름 변경을 미리 보고 변경 파일을 모두 보여 줘” 또는
“이 폼을 검사하고 지원되는 Button 추가를 미리 보여 줘”라고 요청한다. 먼저 검사하고
어댑터가 광고한 타입과 작업을 사용한다. 리팩터링/구조 디자이너 미리보기는 크기가
제한된 불변 토큰과 구체적인 diff를 만든다. 변경을 적용하지 않는다. 해당 미리보기의
적용을 요청하고 승인 카드의 내용을 검토한 뒤 승인하거나 거절한다.

승인은 최대 5분 안에 만료되고 한 번만 사용할 수 있다. Core와 어댑터는 승인 전후와
SDK 실행 직전에 워크스페이스/문서 상태를 검사한다. 프로젝트·구성·문서 등 관련 상태가
바뀌면 새 미리보기/승인이 필요하다. 리팩터링 적용에는 저장된 문서가 필요하며
빌드/테스트도 어댑터의 저장 상태 조건을 만족해야 한다. 실행 전 취소는 작업을 제출하지
않는다. 실행 후 취소/연결 끊김에서는 이미 효과가 반영됐을 수 있으므로 재시도 전에
실제 파일/IDE 상태를 검사한다. 결과가 불확실한 요청을 자동 재실행하지 않는다.

VS 의미 기반 미리보기는 8개 파일, before/after 각 측 합계 128 KiB로 제한한다.
임의 Quick Action, 네이티브 C++ 의미 분석, 최신 out-of-process WinForms,
UWP/실행 중 visual tree 자동화, 임의의 타사 디자이너 컨트롤은 검증 범위 밖이다.
WPF/WinUI는 구조적 문서 편집이며 실행 중 디자이너 객체 자동화가 아니다.
WinUI는 WPF 전용 DockPanel/WrapPanel을 광고하지 않는다. 구체적인 표준 타입과
이벤트 속성은 카탈로그와 검사 결과를 따른다.
실제 fixture에서 WPF/.NET Framework WinForms의 C# 의미 기반 변경,
두 파일 네이티브 Undo와 디자이너 복구를 검증했다. 제한된 VS2022 VB 5/5와 WinUI3
소스 7/7을 통과했고 WinUI3 생성 단계 세 개가 컴파일됐다. WinUI3 실행 앱이나
네이티브 visual designer backend를 검증한 것은 아니다.

## 변경에 맞는 복구 사용

편집기 제안 수락은 IDE의 네이티브 실행 취소를 사용한다. VS 의미 기반 변경은
네이티브 undo context를 사용한다. 설치된 WPF fixture에서 두 파일 rename과 네이티브
Undo로 원본 바이트 복원을 검증했으며 .NET Framework WinForms fixture도 통과했다.
다른 프레임워크는 별도 검증이 필요하다. 일반 사용자 작업은 검증을 위해 Undo를
실행하지 않으므로 결과의 `nativeUndoVerified`는 false로 남을 수 있다.
Core 파일 체크포인트는 기록된 디스크 파일 범위만 다룬다.
디자이너 구조 복구는 소유한 소스/폼/리소스 저널과 별도 복구 미리보기/승인을 사용한다.
대화 복원은 별도 작업이며 디버거·빌드·Git·디자이너 효과를 되돌린다는 약속이 아니다.

디자이너 체크포인트를 복원하려면 현재 문서를 검사하고 반환된 체크포인트 ID로
복구를 미리 본 뒤 diff를 검토하여 별도로 승인한다. 복구에는 변경 후 소유 파일이
그대로 있고 IDE 상태가 저장돼 있어야 한다. 중간에 사용자가 한 편집은 보존해야 한다.
부분 적용/복구는 체크포인트를 유지하고 실제 결과를 보고해야 한다. 계속하기 전에
오류와 보존 파일을 확인하며 다중 파일 원자성을 가정하지 않는다. 격리 VCL/FMX
fixture에서 생성·이벤트 연결·삭제와 세 번의 역순 소스/폼 복원을 검증했다.
실제 RAD 가용성은 저장된 Delphi 소스/폼 쌍, 표준 폼 직접 상속, 정확히 등록된 표준
타입과 허용된 부모를 요구하며 타사/상속된 소유 컴포넌트를 제외한다. 일반 프로젝트
호환성까지 입증한 것은 아니다. 복구 검토는 완전한 원래 텍스트를 표시하고 현재 바이트의
hash/크기를 연결한다. VS 네이티브 복구는 변경 전에 원시 검토 128 KiB, escaped diff
192 KiB와 전체 제안 220 KiB를 검사한다. RAD 구조 변경은 가역적으로 디코딩되는
텍스트 소스/폼 리소스만 지원하며 원래 검토 행 48 KiB와 전체 escaped 제안 220 KiB를
변경 전에 검사한다. 큰 원본은 거절하며 저널만으로 검토 가능한 복구를 입증하지 않는다.

## 로컬 Git 작업

`workspace.git.v1`을 협상한 연결에서는 로컬 상태/diff/이력/브랜치를 요청하고
명시한 파일 스테이징 또는 현재 스테이징 변경 커밋을 미리 본다. 에이전트는 불변
검토 토큰을 받고 적용을 별도로 요청해야 한다. 승인은 캐시된 diff와 커밋 메시지를
표시한다. 스테이징은 index를 바꾸고 커밋은 로컬 Git hook/서명 설정을 따른다.
이 도구는 push·checkout·reset·원격 작업을 제공하지 않는다.

Git 내용 도구는 `.env`, 자격 증명/키 파일, 제외 디렉터리 등
[워크스페이스 경로 제외 정책](WORKSPACE-TOOLS.md)을 공유한다. 관련 추적 변경에
제외 경로가 있으면 diff/스테이징 미리보기를 거절하며 이름 변경의 양쪽 경로와
삭제 경로도 검사한다. 커밋 미리보기는 스테이징된 제외 경로가 하나라도 있으면
거절하므로 해당 변경을 수동으로 처리한 뒤 다시 검토한다. 상태 출력은 제외 경로를
숨긴다. 이력 메시지와 브랜치 이름은 메타데이터이며 이 정책이 전체 이력이나
임의의 허용 파일에서 모든 비밀을 제거한다는 뜻은 아니다.

Git 검토는 5분 뒤 만료되며 스테이징 경로 최대 64개, diff 256 KiB로 제한한다.
링크 경로, 바이너리 변경, 사용자 정의 clean filter, 이미 스테이징 변경이 있는 선택
파일은 수동 검토가 필요하다. 적용은 HEAD/index/status/파일 리비전을 검사하고
다른 작성자의 index lock을 존중하며 별도 index를 사용한다. 커밋 후 index 전달이
실패해도 HEAD는 이미 바뀔 수 있다. `partial`, `outcome_unknown`,
`applied_verification_failed` 결과에서는 재시도 전에 HEAD/index를 검사한다.
동시에 수동으로 ref를 변경하는 경우의 원자성은 보장하지 않는다.

## 제안과 측정

VS **Tools → PiAgent: Suggest Code / Suggest Next Edit**는 현재 버퍼의 제안을
반환하고 네이티브 제안 UI로 수락/실행 취소한다. 안전한 새 파일은 기존 워크스페이스
부모 디렉터리가 필요하다. 경로를 안전하게 연결하지 못한 untitled 문서는 미지원이다.
RAD는 명시적 before/after 미리보기와 수락을 제공하며 네이티브 ghost text/Tab provider는
제공하지 않는다. 큰 저장 버퍼는 UTF-8 64 KiB 안의 16,384 UTF-16 문자 커서 창과
전체 버퍼 리비전을 사용한다. 두 어댑터는 오래된 버퍼/커서/IME 상태를 거절한다.
RAD는 UTF-8 writer 위치와 UTF-16 제안 위치를 변환하며 서로 같은 값으로 취급하지 않는다.

편집기 추론은 도구를 끈 별도 격리 OMP 프로세스를 사용한다. VS는 전체 버퍼
SHA-256과 UTF-16 위치를 포함한 최대 64 KiB 커서 창을 전달할 수 있다. 다음 편집은
그 창 안에 머문다. 대기·시작·구성·첫 토큰·추론·종료를 포함한 총 시간은 소스나
프롬프트를 기록하지 않고 지연을 구분한다. 프로세스 풀링이나 공급자 비용 감소를
주장하지 않는다. 모델·작업·설정·warm/cold 조건·문맥 크기를 맞추어 비교하고
작은 표본으로 신뢰할 만한 p95나 제품 우월성을 주장하지 않는다.
하위 프로세스 종료 결과가 불확실하게 실패하면 다른 추론을 시작하기 전에 해당
편집기 연결을 닫는다. 다시 연결하기 전에 프로세스 결과를 검사한다.

VS 프로파일링은 최신 .NET 대상을 VS에서 디버깅하고 사용 가능한 `dotnet-trace`
백엔드가 필요하다. GC allocation tick은 표본 추정치이며 GC collection duration은
pause time이나 heap snapshot이 아니다. 네이티브 C++/.NET Framework 프로파일링은
미지원이다. RAD CPU 카운터는 실제 시간 대비 kernel/user CPU를 측정하며 함수
스택·할당·Delphi GC를 제공하지 않는다. 같은 워크스페이스/대상 조건에서 어댑터가
발급한 기준 트레이스 ID만 비교한다.

2026-10-09 명시적 측정은 설치된 OMP 18.6.1의 기본
`anthropic/claude-opus-5-5`, minimal effort와 새 격리 프로세스 10개로 합성 코드를
사용했다. 같은 후보 구현에서 각 쌍을 전체 버퍼 → 커서 창의 고정 순서로
전체 버퍼 5회와 커서 창 5회 실행했으며
설치된 0.10.0과의 비교가 아니다.

| 중앙값 측정 | 전체 버퍼 | 커서 창 |
|---|---:|---:|
| 소스 payload | 61,440 bytes | 4,096 bytes |
| OMP 준비 | 647.5 ms | 660.9 ms |
| 제출 후 첫 토큰 | 1,861.0 ms | 1,600.0 ms |
| 종료 포함 총 시간 | 2,669.6 ms | 2,503.2 ms |

10개 응답 모두 유효하고 비어 있지 않은 제안이었다. payload는 93.33% 줄었고
관측 총 시간 중앙값은 6.23% 낮았다. 표본 5개로 통계적으로 신뢰할 만한 속도 개선이나
p95를 입증하지 않는다. 원격 캐시/네트워크 영향을 통제하지 않았고 고정 순서의 편향도
가능하다. 무작위화하거나 순서를 균형 배치한 실험이 아니다. 제안 품질/IDE 수락을
평가하지 않았으며 비용은 제공되지 않았다. 재현 스크립트는
[measure-editor-context.mjs](../scripts/measure-editor-context.mjs)이며 실행마다 명시적 모델 요청을 최대 10회 한다.
로컬 근거: `artifacts/ide-agent-20261009/editor-context-experiment.json`.

## 개발자 검증과 근거

wire 계약은 [IDE-CATALOG-CONTRACT.md](IDE-CATALOG-CONTRACT.md)에 있다.
`npm test`는 직렬 Node/transport 검사, `npm run test:adapters`는 어댑터 통합
검사를 실행한다. 집중 회귀 검사는 카탈로그 소유권/차단, 승인 만료/오래된 상태,
불변 리팩터링/게시/디자이너/Git 검토, 편집기 Unicode/문맥/새 파일,
부분 Git index 전달, 시간 제한 OMP 하위 프로세스 종료를 다룬다. 어댑터 컴파일과
순수 fixture는 설치 IDE/SDK/UI 검증을 대신하지 않는다. 완료라고 판단하기 전에
정확한 후보 바이너리로 빌드/테스트 실패, 네이티브 실행 취소, 디자이너 저장/재로드/복구,
IME/다른 공급자 공존, 취소 결과를 기록한다.
실제 어댑터 미리보기는 `node scripts/validate-designer-contract.mjs <raw-json>`으로
검사할 수 있다. 변경/복구 payload 원본, 대응 검사 결과와 미리보기별
`changeCapturedAt`/`restoreCapturedAt` 근거 시각을 보존한다. 재생 검사는 SDK 변경을
모의 처리하여 Core 승인/토큰 전달을 확인하며 네이티브 저장·빌드·바이트 복원 검증을
대신하지 않는다.
추가 중단 회귀는 실제 ChatSession 소유 프로세스의 갑작스러운 종료 후 OMP 문맥을
복구하고 요청을 자동 재실행하지 않는지 검사한다. 네이티브 턴의 256 KiB 체크포인트
예산 초과에서도 경고 후 파일/Git 상태를 보존하고 다음 턴을 실행하는지 확인한다.

이름 변경/삭제 양쪽 경로와 literal pathspec 처리를 검사했다. 집중 Git/워크스페이스
검사는 15/15를 통과했다. 확장된 전체 검사는 총 209개, 208 PASS, 0 FAIL,
선택 네이티브 RAD receipt 검사 1개 skip으로 완료됐다(148,986.8872 ms,

skip 0개를 통과했다(`adapter-test-0.11.0-final-guidance-both.log`). 서명 어댑터 검증은 최종 DLL의
VS2022 WinForms 8/8·C++ 3/3, VS2026 WPF 11/11·생성 단계 빌드 3개와 실제
